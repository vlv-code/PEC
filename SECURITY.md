## Модель доверия и безопасность

Данный проект реализует избирательный корпоративный доступ к прокси-серверу на основе членства в доменной группе Active Directory:

1. **Active Directory & GPO как шлюз авторизации:**
   - Доставка расширения и распространение токена `extToken` осуществляются исключительно через Group Policy с использованием Security Filtering на группу `SEC-Proxy-VPN`.
   - Пользователи, не входящие в группу, не получают расширение и ключ доступа.
2. **Аутентификация management-API (двухтокенная модель и матрица доступов):**
   - Fleet-токен `EXT_SHARED_TOKEN` (заголовок `X-Fleet-Token` или `X-Ext-Token`) — низкопривилегированный идентификатор парка: предназначен строго для синхронизации расширения и десктопного клиента (`/creds`, `/api/sync`, `/api/app/sync`), bootstrap-регистрации инстансов и скачивания релизов расширения (`GET /api/releases/download/extension/:version`). Намеренно зашивается в артефакты развертывания (CRX, GPO `.reg`, дефолтный профиль клиента). Компрометация fleet-токена НЕ даёт доступа к админке и НЕ позволяет скачивать десктопные бинарные дистрибутивы приложения или MSI-установщики.
   - Админ-токен `ADMIN_TOKEN` (заголовок `X-Admin-Token` или сессионная cookie) открывает все management-API (`/api/builder/*`, `/api/routing/*`, `/api/rotation/*`, `/api/instances/*`, `/api/config`, `/api/status`, управление релизами `/api/releases/*`), а также скачивание десктопных пакетов (`GET /api/releases/download/app/:version` и `/api/releases/download/msi/:version`). Не покидает сервер и никогда не попадает в публичные артефакты. Обязателен при `NODE_ENV=production`; должен отличаться от fleet-токена.
   - Строгая изоляция: fleet-токен на админ-роутах → 401; admin-токен на fleet-роутах → 403; fleet-токен на скачивании app/msi пакетов → 401.
   - Публичными остаются только `/healthz`, `/proxy.pac`, `/updates/*` (для автообновлений Chrome через GPO), `/api/ip-echo` и `/api/sync` (последний проверяет fleet-токен внутри роутера со своим rate limiter'ом). Скачивание ZIP-архива расширения (`/api/extension/download-zip`) требует аутентификации администратора (сессионная кука + CSRF или `X-Admin-Token`) и ограничено rate limiter'ом (10 запросов в минуту).
   - Веб-панель не передает токен в браузер: аутентификация по логину и паролю (scrypt-хеш на сервере) с сессионной cookie (`HttpOnly`, `SameSite=Strict`).

### Матрица прав доступа токенов (Token Permission Matrix)

| Эндпоинт / Ресурс | Публичный (No Auth) | Fleet-токен (`X-Fleet-Token` / `X-Ext-Token`) | Admin-токен (`X-Admin-Token` / Cookie) | Описание |
|-------------------|:-------------------:|:---------------------------------------------:|:--------------------------------------:|----------|
| `GET /healthz`, `/api/ip-echo` | ✅ | ✅ | ✅ | Проверка работоспособности и эхо IP |
| `GET /proxy.pac`, `/updates/*` | ✅ | ✅ | ✅ | Автообновления Chrome CRX и PAC-скрипт (GPO) |
| `GET /creds`, `POST /api/sync` | ❌ | ✅ | ❌ (403) | Синхронизация учетных данных и правил расширения |
| `POST /api/app/sync` | ❌ | ✅ | ❌ (403) | Синхронизация и heartbeat десктопного клиента |
| `GET /api/releases/download/extension/:version` | ❌ | ✅ | ✅ | Скачивание CRX-пакетов расширения |
| `GET /api/releases/download/app/:version` | ❌ | ❌ (401) | ✅ | Скачивание десктопных пакетов приложения (ZIP) |
| `GET /api/releases/download/msi/:version` | ❌ | ❌ (401) | ✅ | Скачивание MSI-установщика Windows |
| `GET /api/extension/download-zip` | ❌ | ❌ (401) | ✅ | Скачивание исходного zip-архива расширения |

| `/api/rotation/*`, `/api/instances/*`, `/api/routing/*` | ❌ | ❌ (401) | ✅ | Управление прокси-узлами, ротацией и инстансами |
3. **Защита от Timing Attacks:**
   - Токен сравнивается по SHA-256-дайджестам через `crypto.timingSafeEqual` (без утечки длины).
3. **Защита от сниффинга пароля в локальной сети:**
   - Рекомендуется использовать директиву `HTTPS xray-host:10809` в PAC-файле (Secure Web Proxy). В этом случае соединение между браузером и прокси шифруется TLS, что исключает перехват заголовка `Proxy-Authorization: Basic ...` в локальной корпоративной сети.
4. **Защита от DNS-утечек:**
   - В PAC-скриптах следует использовать строковые проверки доменов (`dnsDomainIs`, `shExpMatch`) без обращения к `dnsResolve`, чтобы исключить преждевременные запросы к локальному корпоративному DNS.
5. **Ротация учетных данных:**
   - Пароль прокси-инбаунда ротируется через API 3x-ui криптографически стойким генератором (`crypto.randomBytes`).
   - При недоступности панели креды не меняются (защита от рассинхрона флота); standalone-режим — только осознанно, без настроенной панели.
   - Запись файла учетных данных на сервере производится атомарно с правами доступа `0600`.
6. **Подпись пакетов расширения:**
   - `.crx` подписывается в формате CRX3 (RSA-SHA256, protobuf), совместимом с Chrome 70+.
   - Приватный ключ хранится в `extension/key.pem` (gitignored, режим 0600); при деплое в Docker сохраняйте том `pec_extension`, чтобы ID расширения оставался стабильным.
7. **Публичный PAC-эндпоинт (принятый риск):**
   - `GET /proxy.pac` и `/updates/*` не аутентифицируются: браузеры запрашивают PAC-скрипт и CRX-обновления без HTTP-заголовков, авторизация на этом пути технически невозможна.
   - Следствие: любой, у кого есть сетевой доступ к серверу, может прочитать хост/порт прокси и политику маршрутизации (домены разделения).
   - Митигация: сетевая сегментация — сервер PAC-раздачи должен быть доступен только из корпоративных сегментов (firewall / security groups). Для nginx в `deploy/nginx-proxy.conf` есть закомментированный пример allow/deny для `location /proxy.pac` и `location /updates/`.
   - Учетные данные прокси этот эндпоинт не раскрывает: они выдаются только на `/creds` по fleet-токену.
8. **Семантика CIDR-правил PAC (осознанное изменение):**
   - `isInNet(host, ...)` с DNS-именем заставляла браузер делать синхронный DNS-резолв на каждый запрос — при медленном корпоративном DNS это фризило UI пользователей.
   - Теперь CIDR-правила применяются только к host, являющемуся IP-литералом (`/^\d{1,3}(\.\d{1,3}){3}$/`). Хосты, резолвящиеся в RFC1918, покрываются доменными правилами (`*.corp.local` и т.п.); URL с literal-IP продолжают матчиться.
9. **Видимость fleetToken на управляемых эндпоинтах (Windows / Linux) и безопасность профилей:**
   - Файл конфигурации `pec_profile.pbprofile` устанавливается в `%ProgramFiles%\PEC-App\` (или `/etc/pec-client/`) и копируется в `%APPDATA%\PEC-App\profiles\`. Токен `fleetToken` виден локальному интерактивному пользователю.
   - Статические файлы профилей (`pec_profile.pbprofile`, `Default.pbprofile`) и упакованные дистрибутивы НЕ содержат паролей к прокси-узлам (`Password: ""`). Все учетные данные и персонализированные конфигурации доставляются динамически в оперативную память клиента во время защищенного сеанса синхронизации через `POST /api/app/sync` с привязкой к `instanceId`.
   - В соответствии с корпоративной моделью угроз (см. ниже), `fleetToken` является низкопривилегированным идентификатором флота: он позволяет только периодически запрашивать актуальный список прокси-узлов и отправлять heartbeat инстанса. Он строго изолирован от `ADMIN_TOKEN`, не даёт доступа к веб-панели управления и запрещает скачивание десктопных бинарных дистрибутивов через API релизов.
   - Права интерактивных пользователей (IU) на управление службой Windows `PECAppSvc` ограничены строгим дескриптором безопасности SDDL (`(A;;CCLCSWLOCRRC;;;IU)`), запрещающим запуск и остановку службы непривилегированными пользователями.

## Enterprise Threat Model & Architectural Scope

В рамках независимого аудита безопасности и анализа модели угроз были сформулированы проектные архитектурные границы PEC. Следующие 5 предложений аудита **осознанно отклонены** и зафиксированы как проектные границы (Out-of-Scope) в силу фундаментальных ограничений платформы и специфики корпоративных сред:

1. **Client mTLS / устранение общего fleet-токена в расширении MV3**:
   - *Предложение аудита*: Полный отказ от общего токена в пользу строгой PKI/mTLS внутри расширения Chrome.
   - *Обоснование отклонения*: **Технически невозможно.** Любой секрет (сертификат, приватный ключ, токен) внутри Chrome MV3 тривиально извлекается локальным пользователем через `chrome://extensions` (Inspect background page) или чтение SQLite-профиля на диске. Защита PEC строится на том, что API и прокси доступны только в изолированном корпоративном VPN/интранете, доставка расширения выполняется через AD GPO Security Filtering, а учетные данные динамически ротируются.
2. **Cloud HSM / EV Code Signing сертификаты**:
   - *Предложение аудита*: Покупка публичного EV Code Signing сертификата ($500+/год) или аренда Cloud HSM ($1000+/мес).
   - *Обоснование отклонения*: **Неприменимо для self-hosted enterprise.** PEC — полностью онпрем система. В корпоративной среде Windows бинарники и драйверы подписываются внутренним удостоверяющим центром Active Directory Certificate Services (AD CS), чей Root CA автоматически доверен на всех рабочих станциях через домен. В открытом репозитории достаточна верификация SHA-256.
3. **Архитектура D-Bus / Polkit для Linux GTK GUI**:
   - *Предложение аудита*: Переработка Linux GUI на разделение привилегий через D-Bus демон под root и Polkit.
   - *Обоснование отклонения*: **YAGNI и оверинжиниринг.** Linux-клиент PEC с eBPF/cgroups на практике эксплуатируется преимущественно как headless systemd-демон (`deploy/pec-app-linux.service`) на серверах и шлюзах. Разработка сложной шины IPC для десктопного GTK GUI неоправданно усложняет кодовую базу.
4. **Запрет ветки реестра HKCU в GPO**:
   - *Предложение аудита*: Запрет развертывания через ветку реестра `HKCU` и требование только `HKLM`.
   - *Обоснование отклонения*: **Ломает филиальные развертывания.** Во многих компаниях у локальных сисадминов нет прав локального админа на машины пользователей, и они распространяют расширения через User GPO (`HKCU`). Скрипты PEC поддерживают оба скоупа (`-Scope Machine` и `-Scope User`).
5. **Русификация системных логов драйверов и сокетов C-клиента**:
   - *Предложение аудита*: Перевод консольных сообщений драйверов и C-клиентов на русский язык.
   - *Обоснование отклонения*: **Антипаттерн.** Системные логи WinDivert и сокетов на английском — общепринятый стандарт. Это исключает проблемы с кодировками (OEM 866 vs CP1251) в консоли Windows и упрощает парсинг и корреляцию в SIEM-системах.
